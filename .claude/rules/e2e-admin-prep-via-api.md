# Admin-Side E2E Preparation Goes Through the API

When an e2e flow in the user console or on the project admin pages needs admin-side state (a user or keypair, a project, a resource group, a test-only resource policy), the test creates it and cleans it up through the API. It never clicks through admin console pages to prepare or clean up.

## Why

Clicking through admin pages to set up another flow's test is slow and brittle: a change to an unrelated admin page breaks the user console spec, and a failed setup leaves state behind that the next run trips over. An API helper is fast, fails loudly, and pairs every create with a delete.

## Where the line is

The admin console is the `path: 'admin'` subtree under `AdminScopeLayout` in `react/src/routes.tsx` (route scope `admin`, entered through "Switch to Admin Console"), plus the old flat URLs that now redirect there (`/credential`, `/environment`, `/agent`, `/admin-serving` and so on). Its specs live in `e2e/admin/<page>/`.

- **Specs of the admin console itself** (`e2e/admin/<page>/`) act on the admin pages as usual: those pages are what they test. This rule is about preparation for other flows.
- **User console and project admin specs** (`e2e/project/<page>/`, `e2e/project-admin/<page>/`, `e2e/common/<area>/`) do their admin-side preparation and cleanup through the API. The project admin pages `/project/:projectName/admin/*` belong to the user console despite the `admin` in the URL.
- **A flow that touches both consoles** is placed the way `e2e/README.md` says: the screen the test acts on or checks decides, and when unsure, `admin`. When it lands outside `e2e/admin/`, its admin-side setup is preparation and goes through the API.

## Rules

1. **Use the API helpers in `e2e/utils/`**: `admin-api.ts` (`createAdminApiContext`, `gqlAdmin`, `createProjectViaApi`, `createResourceGroupViaApi`, the `purge*ViaApi` and `delete*ViaApi` family) and `test-resources.ts` (`createTestResources`). In `e2e-agent/`, use `e2e-agent/utils/`. Not every file in `e2e/utils/` qualifies: `resource-preset-fixtures.ts` and `deployment-fixtures.ts` create objects other users see (a global or `default`-group resource preset, a public deployment preset), which rule 3 forbids on the shared server, and `cleanup-util.ts` and the deployment page helpers work by driving pages, including `/admin/data`.
2. **Add a missing helper next to the existing ones**, with its delete counterpart, registered for cleanup (`test-resources.ts` or `afterEach`/`afterAll`), and named with the usual `e2e-` prefix (`test-agent-*` for `e2e-agent/` users).
3. **Preparation through the API on the shared server does not create, change or delete server-global settings.** Cluster or domain settings, the `default` or shared resource policies, image registration, rescan or alias, shared resource groups and RBAC (roles, permissions, presets, role assignments of shared accounts) stay off limits for user console and project admin specs, API preparation included. An RBAC screen can still be covered with `page.route` mocks of its responses, and the PR then says the server behaviour is not verified. A test-only role is allowed only in an admin console spec under rule 5. Otherwise a flow that needs one is left out with the reason.
4. **Moving an existing spec's admin-page preparation to the API while fixing it is encouraged.** Keep its assertions as they are. Rule 3 still applies: a preparation that changes a server-global setting (for example editing the `default` keypair resource policy) is not moved to the API; the flow is left out with the reason.
5. **An admin console spec changes server-global settings only on the dedicated admin server, and restores them.** One Playwright run talks to one server, and only a run whose `E2E_PART` includes `admin` loads the admin env file (`includesAdmin` in `playwright.config.ts`, which keeps `E2E_PART` in the workers' environment). A default run (`E2E_PART` unset or `all`) puts `e2e/admin/` on the shared server. So a test under `e2e/admin/` that changes a server-global setting skips itself unless the run selected the admin part: `test.skip(!resolveE2EParts(process.env.E2E_PART).includes('admin'), 'changes server-global settings; runs only with E2E_PART=admin')`, with `resolveE2EParts` from `e2e/e2e-parts.ts`. It restores each change in a fixture or `afterAll`, and never changes settings other specs rely on, such as the login policy or the default resource policies. `e2e-agent/` has no admin part (`e2e.config.ts` always loads `e2e/envs/.env.playwright`), so its tests never change server-global settings.
